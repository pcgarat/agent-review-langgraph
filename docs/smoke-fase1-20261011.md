# Smoke E2E — Fase 1 (report-only)

Guion reproducible para verificar el camino completo: **artefacto del CI → cola →
grafo → comentarios inline + resumen + Teams**, con cero escritura de codigo en el
repo del PR. Complementa `tasks/plan.md` (Task 9) y
`docs/diseno-agente-code-review-20261010.md` (§13).

Hay dos niveles. El **Nivel 1** no necesita red ni credenciales y es el que
recomiendo como "definicion de hecho" diaria; el **Nivel 2** es el smoke real
contra Bitbucket, solo cuando `twg` y los secretos estan disponibles.

---

## 0. Requisitos comunes

- `uv` y el repo clonado; `uv run pytest` verde antes de empezar.
- Para el Nivel 2: `twg login` hecho, un PR de `emotivoo-v2` con cambios y los
  secretos de `.env` (Bitbucket, Teams, `TOOLING_WEBHOOK_SECRET`).
- Variables minimas para el Nivel 2 (ver `.env.example`):
  `BITBUCKET_WORKSPACE`, `BITBUCKET_REPO`, `TEAMS_WEBHOOK_URL`,
  `TOOLING_WEBHOOK_SECRET`, `REDIS_URL`, `DATABASE_URL`.

---

## 1. Nivel 1 — Reproduccion local (sin red)

Prueba el grafo de punta a punta con el diff y el artefacto de PHPStan de
`tests/fixtures/`, usando un VCS falso que ancla como `twg prs diff-line`.

```bash
uv run pytest tests/test_e2e_tooling.py tests/test_worker.py tests/test_graph.py -v
```

**Que demuestra cada cosa:**

| Test | Verifica |
|---|---|
| `test_flujo_completo_estatico_ancla_en_lineas_reales` | Cada hallazgo se ancla a una linea del diff → inline |
| `test_hallazgo_fuera_del_diff_solo_va_al_resumen` | Un hallazgo fuera del PR no se pierde: va al resumen |
| `test_e2e_estatica_y_llm_conviven_y_el_merge_deduplica` | `standards` + `correctness`: el merge deduplica por `(fichero, titulo)` |
| `test_worker_hasta_formato_publica_salida_del_perfil` | Trayecto artefacto en disco → reviewer → inline |
| `test_grafo_sin_hallazgos_no_publica` | PR limpio: ni inline ni resumen |

**Resultado esperado:** los 5 verdes. Si se quiere ver el texto publicado, el
`DiffLineVcs` de los tests guarda `inlines` y `comments`; añadir un `print` o un
`tmp_path` es suficiente.

Estos mismos tests son la red de seguridad de T5–T8; cualquier regresion del
contrato, del anclaje o del merge los rompe.

## 2. Nivel 2 — Smoke real contra Bitbucket

### 2.1 Levantar el stack

```bash
cp .env.example .env    # rellena los secretos (ver §0)
cp ~/.local/bin/twg bin/twg
docker compose up --build -d
docker compose logs -f worker
```

### 2.2 Depositar el artefacto como lo haria el CI

El disparo de Fase 1 **no** es el webhook de PR, sino el `POST` firmado del CI
(ver `docs/ingesta-diferida-ci-20261011.md` §7.1). Se puede simular a mano con un
PR real y el JSON de PHPStan de ese commit:

```bash
PR_ID=417
HEAD_SHA=$(twg bb prs get "$PR_ID" --output json --output-summary none \
  | jq -r '.source.commit.hash')
PAYLOAD=$(jq -c . tests/fixtures/phpstan/analysis.json)

BODY=$(jq -n --arg repo "$BITBUCKET_WORKSPACE/$BITBUCKET_REPO" --argjson pr_id "$PR_ID" \
  --arg head_sha "$HEAD_SHA" --arg pipeline_id "smoke-1" \
  --arg payload "$PAYLOAD" \
  '{repo: $repo, pr_id: $pr_id, head_sha: $head_sha, pipeline_id: $pipeline_id,
    tool: "phpstan", payload: $payload}')

SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$TOOLING_WEBHOOK_SECRET" -r | cut -d' ' -f1)

curl -sS -X POST "http://localhost:8000/webhook/tooling" \
  -H "Content-Type: application/json" -H "X-Reviews-Signature: $SIG" \
  --data-binary "$BODY"
```

**Resultado esperado:** `{"status": "aceptado", "key": "...:smoke-1"}` (202) y, en
los logs del `worker`, `Review completada`. Con `expected_tools: [phpstan]` la
barrera es de 1, asi que este unico artefacto ya dispara la review.

### 2.3 Verificar el resultado en el PR

- **Inline:** debe aparecer **un comentario por hallazgo** anclado a su linea, con
  severidad, titulo, "por que importa" y, si la hay, sugerencia.
- **Resumen:** un unico comentario general con conteo por severidad e indice.
- **Teams:** **una** tarjeta teaser (no una por hallazgo).

Criterio de corte: los inline nunca superan `max_inline_comments` (20); con mas
hallazgos, los P0–P3 mas graves anclan y el resto solo figura en el resumen.

> `twg` no descarga artefactos de pipeline. En el smoke real el JSON debe existir
> en `./var/tooling/<pr_id>/<head_sha>/phpstan.json` (el `POST` lo escribe) o
> pasarse explicitamente. Si el CI aun no publica el `POST`, el barrido de TTL
> encola una review **degradada** (con aviso de "Review incompleta"), que es el
> comportamiento esperado, no un exito silencioso.

## 3. Persona LLM (opcional)

La persona `correctness` es opt-in. Para probarla contra el proveedor real:

```bash
# .env
LLM_REVIEWER_ENABLED=true
LLM_MODEL=<modelo>
LLM_BASE_URL=<endpoint compatible OpenAI; vacio = api.openai.com>
LLM_API_KEY=<clave>
```

Con `LLM_REVIEWER_ENABLED=true` y sin `LLM_MODEL`, el worker **no** construye la
persona y registra un aviso ("Persona LLM habilitada sin LLM_MODEL; se omite").
Verificacion sin red: `tests/test_llm_reviewer.py` cubre salida valida, JSON
invalido, fallo del proveedor, fichero/linea inventados y el tope de hallazgos.

## 4. Checklist de aceptacion (Fase 1)

- [ ] `uv run pytest` y `uv run ruff check src` verdes.
- [ ] `POST /webhook/tooling` firma valida → 202; firma invalida → 401.
- [ ] Review encolada solo con los artefactos completos; TTL → review degradada.
- [ ] Hallazgos anclados en el diff (+ resumen/Teams).
- [ ] Cero llamadas de escritura de codigo en el VCS (sin push/commit/branch).
- [ ] Ningun `Decision.action` es `fix_*` (clamp `max_autonomy: report`).

Con la checklist en verde, la Fase 1 esta hecha y se puede decidir el go/no-go de
la Fase 2 (HITL, Opcion B).
