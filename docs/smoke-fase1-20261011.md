# Smoke E2E — Fase 1 (report-only)

Guion reproducible para verificar el camino completo: **artefacto del CI → cola →
grafo → comentarios inline + resumen + Teams**, con cero escritura de codigo en el
repo del PR. Complementa `docs/diseno-agente-code-review-20261010.md` (§13).

Hay dos niveles. El **Nivel 1** no necesita red ni credenciales y es el que
recomiendo como "definicion de hecho" diaria; el **Nivel 2** es el smoke real
contra Bitbucket, solo cuando `twg` y los secretos estan disponibles.

---

## 0. Requisitos comunes

- `uv` y el repo clonado; `uv run pytest` verde antes de empezar.
- Para el Nivel 2: un **API token scoped de un actor de servicio** de Bitbucket
  (`TWG_BBC_TOKEN`) con un PR de `emotivoo-v2` con cambios, y los
  secretos de `.env` (Teams, `TOOLING_WEBHOOK_SECRET`).
- Variables minimas para el Nivel 2 (ver `.env.example`):
  `TWG_BBC_TOKEN`, `TWG_SITE`, `TWG_USER`, `BITBUCKET_WORKSPACE`,
  `BITBUCKET_REPO`, `TOOLING_WEBHOOK_SECRET`, `REDIS_URL`, `DATABASE_URL`.
  (`TEAMS_WEBHOOK_URL` es opcional: sin ella no hay teaser, pero la review se publica.)

## 1. Nivel 1 — Reproduccion local (sin red)

Prueba el grafo de punta a punta con el diff y el artefacto de PHPStan de
`tests/fixtures/`, usando un VCS falso que ancla como `twg prs diff-line`.

```bash
uv run pytest tests/test_e2e_tooling.py tests/test_worker.py tests/test_graph.py -v
```

**Que demuestra cada cosa:**

| Test | Verifica |
|---|---|
| `test_flujo_completo_estatico_ancla_en_lineas_reales` | Cada hallazgo se ancla a una linea del diff → inline |
| `test_hallazgo_fuera_del_diff_solo_va_al_resumen` | Un hallazgo fuera del PR no se pierde: va al resumen |
| `test_e2e_estatica_y_llm_conviven_y_el_merge_deduplica` | `standards` + `correctness`: el merge deduplica por `(fichero, titulo)` |
| `test_worker_hasta_formato_publica_salida_del_perfil` | Trayecto artefacto en disco → reviewer → inline |
| `test_grafo_sin_hallazgos_no_publica` | PR limpio: ni inline ni resumen |

**Resultado esperado:** los 5 verdes. Si se quiere ver el texto publicado, el
`DiffLineVcs` de los tests guarda `inlines` y `comments`; añadir un `print` o un
`tmp_path` es suficiente.

Estos mismos tests son la red de seguridad del adaptador, las personas y el
publish; cualquier regresion del contrato, del anclaje o del merge los rompe.

## 2. Nivel 2 — Smoke real contra Bitbucket

> El runner `scripts/smoke-nivel2.sh <pr_id>` automatiza §2.1–§2.3 (levanta el
> stack, firma y deposita el artefacto, y recuerda qué verificar). Los pasos de
> abajo quedan como referencia manual y para entender qué hace.

### 2.1 Levantar el stack

```bash
scripts/bootstrap-env.sh   # crea .env, comprueba dependencias
cp ~/.local/bin/twg bin/twg
docker compose up --build -d
docker compose logs -f worker
```

### 2.2 Depositar el artefacto como lo haría el CI

El disparo de Fase 1 **no** es el webhook de PR, sino el `POST` firmado del CI
(ver `docs/ingesta-diferida-ci-20261011.md` §3). Se puede simular a mano con un
PR real y el JSON de PHPStan de ese commit:

```bash
PR_ID=417
HEAD_SHA=$(twg bb prs get "$PR_ID" --output json --output-summary none \
  | jq -r '.source.commit.hash')
PAYLOAD=$(jq -c . tests/fixtures/phpstan/analysis.json)

BODY=$(jq -n --arg repo "$BITBUCKET_WORKSPACE/$BITBUCKET_REPO" --argjson pr_id "$PR_ID" \
  --arg head_sha "$HEAD_SHA" --arg pipeline_id "smoke-1" \
  --arg payload "$PAYLOAD" \
  '{repo: $repo, pr_id: $pr_id, head_sha: $head_sha, pipeline_id: $pipeline_id,
    tool: "phpstan", payload: $payload}')

SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$TOOLING_WEBHOOK_SECRET" -r | cut -d' ' -f1)

curl -sS -X POST "http://localhost:8000/webhook/tooling" \
  -H "Content-Type: application/json" -H "X-Reviews-Signature: $SIG" \
  --data-binary "$BODY"
```

**Resultado esperado:** `{"status": "aceptado", "key": "...:smoke-1"}` (202) y, en
los logs del `worker`, `Review completada`. Con `expected_tools: [phpstan]` la
barrera es de 1, asi que este unico artefacto ya dispara la review.

### 2.3 Verificar el resultado en el PR

- **Inline:** debe aparecer **un comentario por hallazgo** anclado a su linea, con
  severidad, titulo, "por que importa" y, si la hay, sugerencia.
- **Resumen:** un unico comentario general con conteo por severidad e indice.
- **Teams:** **una** tarjeta teaser (no una por hallazgo).

Criterio de corte: los inline nunca superan `max_inline_comments` (20); con mas
hallazgos, los P0–P3 mas graves anclan y el resto solo figura en el resumen.

> `twg` no descarga artefactos de pipeline. En el smoke real el JSON debe existir
> en `./var/tooling/<pr_id>/<head_sha>/phpstan.json` (el `POST` lo escribe). Si el CI aún
> no publica el `POST`, el barrido de TTL encola una review **degradada** (con aviso
> de "Review incompleta"), que es el comportamiento esperado. El artefacto es un
> **puente desechable**, no la cimentación (`docs/ingesta-diferida-ci-20261011.md` §4).

## 3. Persona LLM (opcional)

La persona `correctness` es opt-in. Para probarla contra el proveedor real:

```bash
# .env
LLM_REVIEWER_ENABLED=true
LLM_MODEL=<modelo>
LLM_BASE_URL=<endpoint compatible OpenAI; vacio = api.openai.com>
LLM_API_KEY=<clave>
```

Con `LLM_REVIEWER_ENABLED=true` y sin `LLM_MODEL`, el worker **no** construye la
persona y registra un aviso ("Persona LLM habilitada sin LLM_MODEL; se omite").
Verificacion sin red: `tests/test_llm_reviewer.py` cubre salida valida, JSON
invalido, fallo del proveedor, fichero/linea inventados y el tope de hallazgos.

## 5. Nivel 2 ejecutado (2026-10-11, PR 430 de `cqm/emotivoo-v2`)

Ejecucion real de `scripts/smoke-nivel2.sh` contra el PR
[430](https://bitbucket.org/cqm/emotivoo-v2/pull-requests/430) (`head_sha`
`de6d4e40cd0f`), con un artefacto de PHPStan **correspondiente a ese PR** (4
hallazgos anclables) para que el anclaje inline fuese representativo.

**Resultado** (publicado en el PR):

- **4 inline**, uno por hallazgo, anclados a lineas reales del diff: 3 en
  `src/Shared/Domain/PortalUser/Model/PortalUser.php` (L70, L303, L313) y 1 en
  `migrations/Version20261008140000.php` (L39). Ninguno supero el tope de 20.
- **Resumen** unico: `4 hallazgos · 4 inline · 0 solo en resumen`, con pie
  `<!-- reviews:…:ok -->`.
- **Scope**: 67 ficheros → 10 revisados (`max_files_per_pr`).
- **Clamp**: las 4 decisiones son `report`; la de la migracion conserva la razon
  del guard `never_auto_paths`.
- **Dedupe** (comportamiento vigente en el smoke; **revisado despues**, ver
  `docs/decisiones-publish-inline-20261011.md` §Q1): el reenvio del mismo
  `pipeline_id` no re-publica. Un `pipeline_id` **nuevo** sobre el mismo commit
  publica su propia review (el pie se ancla ahora a la *ejecucion*, no al commit).
- **Firma**: invalida y ausente → `401`.
- **Latencia** (P5, orientativa): ~15 s de review para 4 hallazgos, con 4
  subprocess a `twg` para resolver anclas. Refuerza que la cola secuencial es el
  cuello en PRs grandes.

> Teams quedo en no-op (`TEAMS_WEBHOOK_URL` vacio manda la tarjeta al vacio sin
> fallar). La verificacion de la tarjeta necesita un Incoming Webhook real.

### Fallos que solo afloran con Docker (encontrados al ejecutar)

Ambos habrian impedido **cualquier** review en un despliegue, y ninguno lo
detectaba el Nivel 1 (que no usa contenedores):

1. **Worker en crash-loop.** `redis-py` 8 fija un `socket_timeout` de 5 s por
   defecto; el `BLPOP timeout=5` competia con ese deadline y una cola vacia
   elevaba `TimeoutError`, matando al proceso en cada vuelta. Corregido: cliente
   sin deadline de socket para operaciones bloqueantes + `dequeue` tolerante a
   fallos transitorios.
2. **Contrato fuera de la imagen.** `contracts/findings-schema.json` se resolvia
   relativo al paquete instalado (`site-packages` dentro del contenedor), asi que
   validar el primer `Finding` fallaba con `FileNotFoundError`. Corregido: la
   ruta prueba candidatos (repo, `/app/contracts`) y el `Dockerfile` copia
   `contracts/`.

Ademas, la autenticacion de `twg` (que vive en el host, no en la imagen) hay que
inyectarla en el worker; el script del smoke ahora lo hace.
